# 최태권 - Contribution Document

## 담당 서비스

### API Gateway
- **역할**: 라우팅, JWT 검증, Rate Limiting, Circuit Breaker
- **핵심 구현**:
  - Spring Cloud Gateway 기반 Reactive 라우팅
  - `/internal/**` 경로 차단 필터 (내부 API 보안)
  - Resilience4j Circuit Breaker 통합

### Event Service
- **역할**: 공연/공연장/좌석 관리, Redis 캐싱, Kafka Consumer
- **핵심 구현**:
  - Redis 캐싱 전략 (공연 목록/상세/좌석)
  - Kafka Consumer: 좌석 상태 업데이트 (`payment.events`, `reservation.events`)
  - 내부 API: `/internal/seats/status/{scheduleId}` (SOLD 좌석 조회)

### Queue Service
- **역할**: Redis Sorted Set 기반 대기열, 배치 승인, Token 발급
- **핵심 구현**:
  - Lua Script 원자적 배치 승인 (10명/초)
  - 대기열 용량 제한 (50,000명/회차)
  - 중복 대기 방지 (`queue:active:{userId}`)

## 핵심 기술적 도전과 해결 (SPSL 형식)

### 1. Redis KEYS 명령 금지 → SET 자료구조 전환

**상황 (Situation)**
- 좌석 상태 조회 시 HOLD 상태 좌석을 빠르게 찾아야 함
- 초기 설계: `seat:hold:{scheduleId}:{seatId}` 키 패턴 사용

**문제 (Problem)**
- Redis `KEYS seat:hold:{scheduleId}:*` 명령은 O(N) 복잡도
- 대기열에서 수만 명이 동시 조회 시 Redis 전체 DB 스캔 → 성능 저하

**해결 (Solution)**
- `hold_seats:{scheduleId}` SET 자료구조 도입
  - HOLD 시: `SADD hold_seats:{scheduleId} {seatId}`
  - 해제 시: `SREM hold_seats:{scheduleId} {seatId}`
  - 조회: `SMEMBERS hold_seats:{scheduleId}` (O(N)이지만 N은 HOLD 좌석 수만큼)
- Reservation Service에 API 제공: `/internal/seats/hold/{scheduleId}`

**배운 점 (Learning)**
- Redis 운영 환경에서 KEYS/SCAN 명령 금지가 필수임을 체감
- O(1) 자료구조 선택이 대규모 트래픽 환경에서 생존 조건

**관련 파일**:
- `queue-service/src/main/kotlin/com/ticketqueue/queue/service/QueueService.kt`
- `event-service/src/main/kotlin/com/ticketqueue/event/controller/InternalSeatController.kt`

### 2. API Gateway `/internal/**` 경로 차단 필터 구현

**상황 (Situation)**
- 서비스 간 내부 API (`/internal/**`)를 외부에 노출하면 안 됨
- 하지만 API Gateway는 모든 경로를 라우팅

**문제 (Problem)**
- 기본 라우팅 규칙만으로는 `/internal/**` 차단 불가
- Security Filter로 막으면 서비스 간 통신도 차단됨

**해결 (Solution)**
- Spring Cloud Gateway `GatewayFilter` 커스텀 필터 구현
  ```kotlin
  @Component
  class InternalPathBlockFilter : GlobalFilter, Ordered {
      override fun filter(exchange: ServerWebExchange, chain: GatewayFilterChain): Mono<Void> {
          val path = exchange.request.uri.path
          if (path.startsWith("/internal/")) {
              exchange.response.statusCode = HttpStatus.NOT_FOUND
              return exchange.response.setComplete()
          }
          return chain.filter(exchange)
      }
      override fun getOrder() = -100  // Security 필터보다 먼저 실행
  }
  ```
- 내부 API는 `X-Service-Api-Key` 헤더로 서비스 간 직접 호출

**배운 점 (Learning)**
- Gateway 레벨 보안 정책의 중요성
- Filter Order 우선순위 설정으로 Security 우회 가능

**관련 파일**:
- `api-gateway/src/main/kotlin/com/ticketqueue/gateway/filter/InternalPathBlockFilter.kt`

### 3. Kafka Consumer: 좌석 상태 동기화 (Event Service)

**상황 (Situation)**
- Reservation Service에서 예매 확정 시 좌석 상태를 SOLD로 변경해야 함
- Event Service는 공연/좌석 데이터의 Owner

**문제 (Problem)**
- REST API 동기 호출 시 장애 전파 위험
- Reservation Service가 Event Service 장애 시 블로킹

**해결 (Solution)**
- Kafka 이벤트 기반 비동기 처리
  1. Payment Service → `PaymentSuccess` 발행
  2. Reservation Service (Consumer) → 예매 CONFIRMED
  3. Reservation Service → `ReservationConfirmed` 발행
  4. Event Service (Consumer) → 좌석 상태 SOLD
- 멱등성 보장: `common.processed_events` 테이블 활용

**배운 점 (Learning)**
- 서비스 간 상태 동기화는 이벤트 기반이 안전
- Consumer 멱등성 설계의 중요성 (중복 처리 방지)

**관련 파일**:
- `event-service/src/main/kotlin/com/ticketqueue/event/consumer/ReservationEventConsumer.kt`
- `event-service/src/main/kotlin/com/ticketqueue/event/service/SeatService.kt`

## 개인 아키텍처 의사결정

### 1. Queue Service: Lua Script 원자적 배치 승인
- **결정**: Redis Lua Script로 `ZRANGE` + `ZREM` + Token 발급을 원자적으로 처리
- **근거**:
  - Redis Single Thread 특성상 Lua Script는 원자성 보장
  - 10명/초 배치 승인 시 Race Condition 방지
- **트레이드오프**:
  - Lua Script 디버깅 어려움
  - 하지만 성능과 정합성 확보

### 2. Event Service: Redis 캐싱 TTL 5분
- **결정**: 공연 목록/상세 캐시 TTL을 5분으로 설정
- **근거**:
  - 공연 정보는 자주 변하지 않음
  - 캐시 히트율 극대화로 DB 부하 감소
- **트레이드오프**:
  - 최대 5분 지연 허용 (비즈니스 요구사항 충족)

## 코드 하이라이트

### 1. Lua Script 원자적 배치 승인
**파일**: `queue-service/src/main/resources/lua/batch-approve.lua`
```lua
local queueKey = KEYS[1]
local batchSize = tonumber(ARGV[1])
local now = tonumber(ARGV[2])

-- ZRANGE로 상위 N명 추출
local users = redis.call('ZRANGE', queueKey, 0, batchSize - 1)

if #users > 0 then
    -- ZREM으로 원자적 제거
    redis.call('ZREM', queueKey, unpack(users))
end

return users
```

**특징**:
- `ZRANGE` + `ZREM`을 단일 원자 연산으로 처리
- Race Condition 완전 방지
- 10명/초 처리량 보장

### 2. API Gateway InternalPathBlockFilter
**파일**: `api-gateway/src/main/kotlin/com/ticketqueue/gateway/filter/InternalPathBlockFilter.kt`

**특징**:
- Global Filter로 모든 요청 검사
- Order -100으로 Security 필터보다 우선 실행
- 404 반환으로 경로 존재 여부 숨김

## 회고 및 성장

### 다시 한다면 다르게 할 점

1. **Redis Pub/Sub 모니터링 강화**:
   - Redisson 분산 락 디버깅 어려움 경험
   - 다음에는 Redis Slowlog, Latency Monitor 설정 필수

2. **Kafka Consumer Lag 모니터링**:
   - 이벤트 처리 지연 시 원인 파악 어려움
   - Kafka UI + CloudWatch Metrics 연동 필요

3. **Lua Script 테스트 전략**:
   - Lua Script 단위 테스트 부재
   - TestContainers + Redis로 통합 테스트 필수

### 성장한 기술 역량

1. **Redis 운영 지식**:
   - KEYS 명령 위험성, SET/Hash 자료구조 활용
   - TTL 관리, Memory Eviction Policy 이해

2. **Kafka Consumer 설계**:
   - 멱등성 보장 패턴 (processed_events 테이블)
   - At-least-once + 멱등성 = Exactly-once 효과

3. **Spring Cloud Gateway 실전 경험**:
   - Reactive 프로그래밍 (Mono/Flux)
   - Custom Filter 구현 및 Order 우선순위 관리

4. **MSA 통합 경험**:
   - 서비스 간 계약(Contract) 중요성
   - 내부 API 보안, Kafka 스키마 버전 관리
