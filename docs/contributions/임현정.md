# 임현정 - Contribution Document

## 담당 서비스

### User Service
- **역할**: 인증, 회원관리, OAuth2, reCAPTCHA, 본인인증
- **핵심 구현**:
  - JWT + RTR (Refresh Token Rotation) 인증 시스템
  - reCAPTCHA v2 통합 (봇 차단) 및 서킷 브레이커 적용
  - PortOne CI/DI 본인인증 (1인 1계정 강제) 및 서킷 브레이커 적용
  - 예외 계층 분리(`UserException` vs `ExternalSystemException`)를 통한 서킷 브레이커 정밀 운영
  - 외부 API 호출과 DB 트랜잭션 분리 (AuthTransactionalService)

### Reservation Service
- **역할**: 좌석 선점, 예매 관리, Redisson 분산 락, Outbox Pattern
- **핵심 구현**:
  - **Redisson MultiLock 기반 원자적 선점**: 사용자별 요청 락과 다중 좌석 락을 통합 관리하여 선점 로직 보호.
  - **데드락(Deadlock) 방지**: 다중 좌석 락 획득 시 좌석 ID를 정렬하여 순환 대기 조건 제거.
  - **TOCTOU 경쟁 조건 해결**: 사용자-회차별 분산 락을 통해 최대 예매 수량 검증 로직의 원자성 보장.
  - `hold_seats:{scheduleId}` SET 관리 (HOLD 좌석 목록 실시간 오버레이)
  - Transactional Outbox Pattern (`ReservationCancelled` 이벤트 발행)

### Payment Service
- **역할**: PortOne 연동, SAGA 오케스트레이션, 보상 트랜잭션
- **핵심 구현**:
  - SAGA Orchestrator 역할 (결제 성공/실패 플로우 관리)
  - PortOne Prepare/Confirm API 연동
  - Transactional Outbox Pattern (`PaymentSuccess`, `PaymentFailed` 이벤트 발행)

## 핵심 기술 및 예상 문제 상황

### 1. Redisson 분산 락: Spin Lock vs Pub/Sub

**상황 (Situation)**
- 마지막 1석을 두고 수백 명이 동시에 예매 시도
- 동시성 제어 없이는 이중 선점 발생

**문제 (Problem)**
- 기본 Redisson `tryLock()` (Spin Lock) 사용 시 Redis 부하 증가
- 수백 명이 동시에 락 획득 시도 → Redis CPU 100%

**해결방안 (Solution)**
- Redisson Pub/Sub 기반 Lock 사용
  ```kotlin
  val lock = redissonClient.getLock("seat:hold:${scheduleId}:${seatId}")
  val acquired = lock.tryLock(15, 300, TimeUnit.SECONDS)  // 15초 대기, 300초 보유
  if (acquired) {
      try {
          // 좌석 선점 로직
          reservationRepository.save(reservation)
          redisTemplate.opsForSet().add("hold_seats:$scheduleId", seatId)
      } finally {
          lock.unlock()
      }
  }
  ```
- Pub/Sub 방식: 락 해제 시 Subscribe 중인 스레드만 알림 → 폴링 부하 감소

### 2. SAGA Orchestration + Transactional Outbox Pattern

**상황 (Situation)**
- 결제 성공 → 예매 확정 → 좌석 상태 SOLD 플로우에서 중간 장애 발생 가능
- 예: 결제 성공했지만 Reservation Service 장애 → 예매 미확정

**문제 (Problem)**
- DB 커밋 후 Kafka 발행 전 장애 시 이벤트 유실
- 재시도 시 중복 발행 위험

**해결방안 (Solution)**
1. **Transactional Outbox Pattern**:
   - Payment Service에서 결제 성공 시 `common.outbox_events` 테이블에 INSERT (동일 트랜잭션)
   - Outbox Poller가 1초마다 미발행 이벤트를 Kafka로 발행
   - 발행 성공 시 `published = TRUE` 업데이트

2. **SAGA Orchestration**:
   - Payment Service가 SAGA 진행 상황 관리
   - 성공: `PaymentSuccess` → Reservation CONFIRMED → Event SOLD
   - 실패: `PaymentFailed` → Reservation CANCELLED → Event AVAILABLE

### 3. JWT + RTR (Refresh Token Rotation) 구현

**상황 (Situation)**
- JWT 기반 인증 시 Refresh Token 탈취 위험
- 탈취된 Refresh Token으로 무제한 Access Token 발급 가능

**문제 (Problem)**
- Refresh Token의 긴 TTL(7일)로 탈취 시 피해 확대
- 일반적인 Refresh Token은 재사용 가능 → 탈취 감지 어려움

**해결방안 (Solution)**
- **RTR (Refresh Token Rotation) 패턴 적용**:  
  [1] 토큰 갱신 시 신규 Refresh Token 발급  
  [2] 기존 Refresh Token 즉시 폐기 (DB 삭제)  
  [3] `token_family` 개념 도입: 동일 로그인 세션의 토큰 그룹  
  [4] 폐기된 토큰 재사용 감지 시 `token_family` 전체 무효화 (탈취 감지)

## 협업 및 커뮤니케이션

### 업무 분담 방식
- **A개발자**: API Gateway, Event Service, Queue Service
- **B개발자 (본인)**: User Service, Reservation Service, Payment Service
- **통합 포인트**:
  - Kafka 이벤트 스키마 협의 (`payment.events`, `reservation.events`)
  - Redis Key 패턴 공유 (`hold_seats:{scheduleId}`)
  - 내부 API 명세 작성 (`/internal/**`)

### 서비스 간 통합 포인트
1. **Reservation Service → Event Service**:
   - 내부 API: `/internal/seats/status/{scheduleId}` (SOLD 좌석 조회)
   - Feign Client 사용, Timeout 10초, Circuit Breaker 적용

2. **Payment Service → Reservation Service**:
   - Kafka 이벤트: `PaymentSuccess`, `PaymentFailed`
   - Reservation Consumer: 예매 확정/취소 처리

3. **Reservation Service → Event Service**:
   - Kafka 이벤트: `ReservationCancelled`
   - Event Consumer: 좌석 선점 해제

### PR/코드 리뷰 프로세스
- **브랜치 전략**: feature/* → develop → main
- **PR 규칙**:
  - 제목: `작업유형: 작업 내용 #이슈번호` (예: `feat: 분산 락 구현 #11`)
  - 설명: 요약, 변경 사항, 테스트 방법, 관련 요구사항 ID
- **리뷰 포인트**:
  - Outbox Pattern 누락 여부
  - Consumer 멱등성 보장 여부
  - Redisson Lock finally 블록 확인
