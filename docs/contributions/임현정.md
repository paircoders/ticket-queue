## 핵심 기술적 도전과 해결 (SPSL 형식)

### 1. Redisson 분산 락: Spin Lock vs Pub/Sub

**상황 (Situation)**
- 마지막 1석을 두고 수백 명이 동시에 예매 시도
- 동시성 제어 없이는 이중 선점 발생

**문제 (Problem)**
- 기본 Redisson `tryLock()` (Spin Lock) 사용 시 Redis 부하 증가
- 수백 명이 동시에 락 획득 시도 → Redis CPU 100%

**해결 (Solution)**
- Redisson Pub/Sub 기반 Lock 사용
  ```kotlin
  val lock = redissonClient.getLock("seat:hold:${scheduleId}:${seatId}")
  val acquired = lock.tryLock(15, 300, TimeUnit.SECONDS)  // 15초 대기, 300초 보유
  if (acquired) {
      try {
          // 좌석 선점 로직
          reservationRepository.save(reservation)
          redisTemplate.opsForSet().add("hold_seats:$scheduleId", seatId)
      } finally {
          lock.unlock()
      }
  }
  ```
- Pub/Sub 방식: 락 해제 시 Subscribe 중인 스레드만 알림 → 폴링 부하 감소

**배운 점 (Learning)**
- Redisson 내부 메커니즘 이해 (Spin Lock vs Pub/Sub)
- 대기 시간 15초, 보유 시간 300초(5분) 설정의 중요성
- TTL 만료 시 자동 해제로 데드락 방지

**관련 파일**:
- `reservation-service/src/main/kotlin/com/ticketqueue/reservation/service/ReservationService.kt`
- `reservation-service/src/main/kotlin/com/ticketqueue/reservation/config/RedissonConfig.kt`

### 2. SAGA Orchestration + Transactional Outbox Pattern

**상황 (Situation)**
- 결제 성공 → 예매 확정 → 좌석 상태 SOLD 플로우에서 중간 장애 발생 가능
- 예: 결제 성공했지만 Reservation Service 장애 → 예매 미확정

**문제 (Problem)**
- DB 커밋 후 Kafka 발행 전 장애 시 이벤트 유실
- 재시도 시 중복 발행 위험

**해결 (Solution)**
1. **Transactional Outbox Pattern**:
   - Payment Service에서 결제 성공 시 `common.outbox_events` 테이블에 INSERT (동일 트랜잭션)
   - Outbox Poller가 1초마다 미발행 이벤트를 Kafka로 발행
   - 발행 성공 시 `published = TRUE` 업데이트

2. **SAGA Orchestration**:
   - Payment Service가 SAGA 진행 상황 관리
   - 성공: `PaymentSuccess` → Reservation CONFIRMED → Event SOLD
   - 실패: `PaymentFailed` → Reservation CANCELLED → Event AVAILABLE

**배운 점 (Learning)**
- Outbox Pattern이 이벤트 유실 방지의 핵심
- At-least-once 전달 + Consumer 멱등성 = Exactly-once 효과
- SAGA Orchestration이 Choreography보다 실패 추적 용이

**관련 파일**:
- `payment-service/src/main/kotlin/com/ticketqueue/payment/service/PaymentService.kt`
- `common/src/main/kotlin/com/ticketqueue/common/outbox/OutboxPublisher.kt`
- `reservation-service/src/main/kotlin/com/ticketqueue/reservation/consumer/PaymentEventConsumer.kt`

### 3. JWT + RTR (Refresh Token Rotation) 구현

**상황 (Situation)**
- JWT 기반 인증 시 Refresh Token 탈취 위험
- 탈취된 Refresh Token으로 무제한 Access Token 발급 가능

**문제 (Problem)**
- Refresh Token의 긴 TTL(7일)로 탈취 시 피해 확대
- 일반적인 Refresh Token은 재사용 가능 → 탈취 감지 어려움

**해결 (Solution)**
- **RTR (Refresh Token Rotation) 패턴 적용**:
  1. 토큰 갱신 시 신규 Refresh Token 발급
  2. 기존 Refresh Token 즉시 폐기 (DB 삭제)
  3. `token_family` 개념 도입: 동일 로그인 세션의 토큰 그룹
  4. 폐기된 토큰 재사용 감지 시 `token_family` 전체 무효화 (탈취 감지)

**배운 점 (Learning)**
- RTR이 XSS 공격 피해 최소화에 효과적
- `token_family` 개념으로 탈취 여부 즉시 감지 가능
- DB 기반 Refresh Token 관리가 필수 (Redis는 TTL 만료 시 데이터 유실)

**관련 파일**:
- `user-service/src/main/kotlin/com/ticketqueue/user/service/AuthService.kt`
- `user-service/src/main/kotlin/com/ticketqueue/user/entity/RefreshToken.kt`

## 개인 아키텍처 의사결정

### 1. Redisson 대기/보유 시간 설정
- **결정**: `tryLock(15초 대기, 300초 보유)`
- **근거**:
  - 대기 시간 15초: 대부분의 락은 5초 내 해제 (좌석 선점 로직 단순)
  - 보유 시간 300초: 좌석 선점 유효 기간(5분)과 동일
- **트레이드오프**:
  - 15초 대기로 사용자 경험 저하 가능
  - 하지만 15초 내 락 획득 실패 시 재시도 유도

### 2. Outbox Poller 주기 1초
- **결정**: Outbox 테이블을 1초마다 폴링하여 Kafka 발행
- **근거**:
  - 이벤트 처리 지연 최소화 (사용자 체감 가능)
  - DB 부하 vs 실시간성 트레이드오프에서 실시간성 우선
- **트레이드오프**:
  - 1초마다 SELECT 쿼리 → DB 부하 증가
  - 대안: Debezium CDC (향후 도입 고려)

### 3. processed_events 테이블 복합 PK
- **결정**: `(event_id, consumer_service)` 복합 Primary Key
- **근거**:
  - 동일 이벤트를 여러 Consumer가 각각 처리 가능
  - Unique Constraint로 원자적 중복 체크 (Race Condition 방지)
- **트레이드오프**:
  - 테이블 크기 증가 (7일 후 자동 삭제로 관리)

## 코드 하이라이트

### 1. Redisson 분산 락 + 좌석 선점
**파일**: `reservation-service/src/main/kotlin/com/ticketqueue/reservation/service/ReservationService.kt`
```kotlin
@Transactional
fun holdSeat(userId: UUID, scheduleId: UUID, seatId: UUID): Reservation {
    val lockKey = "seat:hold:$scheduleId:$seatId"
    val lock = redissonClient.getLock(lockKey)

    val acquired = lock.tryLock(15, 300, TimeUnit.SECONDS)
    if (!acquired) {
        throw SeatAlreadyHoldException("좌석이 이미 선점되었습니다")
    }

    try {
        // 1. DB 예매 생성 (PENDING)
        val reservation = Reservation(
            userId = userId,
            scheduleId = scheduleId,
            seatId = seatId,
            status = ReservationStatus.PENDING,
            holdExpiresAt = LocalDateTime.now().plusMinutes(5)
        )
        reservationRepository.save(reservation)

        // 2. Redis SET에 HOLD 좌석 추가
        redisTemplate.opsForSet().add("hold_seats:$scheduleId", seatId.toString())

        return reservation
    } finally {
        lock.unlock()
    }
}
```

**특징**:
- Pub/Sub 기반 Lock으로 Redis 부하 최소화
- DB + Redis 원자적 처리 (트랜잭션 범위 내)
- finally 블록으로 락 해제 보장

### 2. Transactional Outbox Pattern
**파일**: `payment-service/src/main/kotlin/com/ticketqueue/payment/service/PaymentService.kt`
```kotlin
@Transactional
fun confirmPayment(paymentKey: String, amount: BigDecimal): Payment {
    // 1. PortOne 결제 승인
    val portOneResult = portOneClient.confirm(paymentKey, amount)

    // 2. DB Payment 상태 업데이트
    val payment = paymentRepository.findByPaymentKey(paymentKey)
    payment.status = PaymentStatus.SUCCESS
    paymentRepository.save(payment)

    // 3. Outbox 이벤트 저장 (동일 트랜잭션)
    val event = OutboxEvent(
        aggregateType = "Payment",
        aggregateId = payment.id,
        eventType = "PaymentSuccess",
        payload = objectMapper.writeValueAsString(PaymentSuccessEvent(payment))
    )
    outboxEventRepository.save(event)

    return payment
}
```

**특징**:
- DB 커밋과 Outbox INSERT가 동일 트랜잭션
- Kafka 발행 실패해도 이벤트 유실 없음
- Outbox Poller가 재시도 (최대 3회)

## 협업 및 커뮤니케이션

### 업무 분담 방식
- **A개발자**: API Gateway, Event Service, Queue Service
- **B개발자 (나)**: User Service, Reservation Service, Payment Service
- **통합 포인트**:
  - Kafka 이벤트 스키마 협의 (`payment.events`, `reservation.events`)
  - Redis Key 패턴 공유 (`hold_seats:{scheduleId}`)
  - 내부 API 명세 작성 (`/internal/**`)

### 서비스 간 통합 포인트
1. **Reservation Service → Event Service**:
   - 내부 API: `/internal/seats/status/{scheduleId}` (SOLD 좌석 조회)
   - Feign Client 사용, Timeout 10초, Circuit Breaker 적용

2. **Payment Service → Reservation Service**:
   - Kafka 이벤트: `PaymentSuccess`, `PaymentFailed`
   - Reservation Consumer: 예매 확정/취소 처리

3. **Reservation Service → Event Service**:
   - Kafka 이벤트: `ReservationCancelled`
   - Event Consumer: 좌석 선점 해제

### PR/코드 리뷰 프로세스
- **브랜치 전략**: feature/* → develop → main
- **PR 규칙**:
  - 제목: `[서비스명] 작업 내용` (예: `[Reservation] 분산 락 구현`)
  - 설명: 변경 이유, 테스트 방법, 관련 요구사항 ID
- **리뷰 포인트**:
  - Outbox Pattern 누락 여부
  - Consumer 멱등성 보장 여부
  - Redisson Lock finally 블록 확인

## 회고 및 성장

### 다시 한다면 다르게 할 점

1. **Redisson Lock 타임아웃 모니터링**:
   - 락 획득 실패율 측정 미흡
   - CloudWatch Metrics로 `tryLock` 성공/실패율 추적 필요

2. **Outbox Poller 성능 최적화**:
   - 1초마다 SELECT 쿼리 → DB Connection Pool 고갈 위험
   - Debezium CDC 도입 고려 (DB 부하 감소)

3. **PortOne API 에러 핸들링 강화**:
   - Timeout, 네트워크 오류 시 재시도 전략 부족
   - 지수 백오프 + Circuit Breaker 설정 세밀화 필요

### 성장한 기술 역량

1. **분산 락 실전 경험**:
   - Redisson Pub/Sub 메커니즘 이해
   - Lock Timeout 설정의 중요성 (데드락 방지)
   - Race Condition 디버깅 능력

2. **SAGA 패턴 설계 능력**:
   - Orchestration vs Choreography 선택 기준
   - 보상 트랜잭션 설계 (실패 시 롤백 플로우)
   - 이벤트 스키마 버전 관리

3. **Kafka 운영 지식**:
   - Consumer Lag 모니터링
   - 멱등성 보장 패턴 (processed_events 테이블)
   - DLQ 처리 전략

4. **보안 인증 설계**:
   - JWT + RTR 패턴 구현
   - token_family 기반 탈취 감지
   - reCAPTCHA 통합 (봇 차단)
